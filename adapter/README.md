# 平台适配层（UNVERIFIED，本目录只有说明，没有代码）

`core/actions.py` 里的三个方法是桩：只打印 WOULD。把骨架变成真实工具，需要在本目录补一层适配代码。以下每一条都是 UNVERIFIED——本仓库没有在任何真实系统上执行过路由或代理变更。

## 1. 适配层要兑现的契约

- `on_prebuild(node_b)`：在不抢占默认路由的前提下，让 B 达到"可承载"状态（链路可用、按需完成认证、探测可走通）。它必须是**非破坏性**的：失败不能影响正在承载的 A。
- `on_swap(node_b)`：把默认出口指向 B。要求可重复调用不产生叠加副作用（幂等），并且执行前留下足够信息用于回滚。
- `on_rollback(node_a)`：把出口恢复到 A，恢复到什么程度要与 swap 前的快照对齐，而不是"大概切回去"。

## 2. 改路由 metric

需要处理的事：读取并保存当前默认路由与 metric 快照；用更高优先级（更低 metric）指向 B；验证新默认路由生效；失败时按快照恢复。各平台差异（UNVERIFIED）：

- **Windows**：路由表与接口 metric 是两套东西，修改通常需要管理员权限；还要考虑多网卡并存时的优先级。
- **Linux**：主路由表之外可能还有策略路由与多规则表，改了主表不代表流量真的走 B；网络管理器可能随时把手工改动覆盖回去。
- **macOS**：服务顺序与路由表相互影响，提权方式与 Linux 不同。
- **OpenWrt**：通常由网络配置守护进程统一管理，手工改的运行时状态可能在 reload 后丢失。

不要假设在一个平台验证过的步骤能照搬到另一个平台。

## 3. 调代理分流

如果不改系统路由，而是让代理客户端按节点分流，那么"切换"的对象是代理的出站规则：需要确认分流规则的热更新方式、是否要求重启核心、以及规则切换对存量连接的处理。哪些流量走代理、哪些绕过代理，也要在适配层明确，否则逻辑层的"上游质量"与被代理流量的真实路径可能对不上（UNVERIFIED）。

## 4. 权限提权

路由变更普遍需要提权。需要决定：整个进程常驻提权，还是只把变更动作交给一个受控的小助手进程；如何限制这个助手只接受预先定义的几种操作；提权失败时逻辑层收到什么错误、状态机应停在哪个状态。以上均未在任何系统验证（UNVERIFIED）。

## 5. 安全与可恢复性要求

- 默认 dry-run：先打印将执行的变更，由人确认后才允许真正执行。
- 每次变更留快照与日志，回滚路径必须与切换路径一起测试，而不是事后补。
- 提供紧急停止：停止后不再发出任何切换动作，并保持当前出口不变。
- 不要在生产网络上做并发认证实验；认证相关行为先在受控环境验证，见 docs/unverified.md 第 2 条。

## 6. 建议的接入顺序（UNVERIFIED）

1. 只读：实现真实 ProbeSource，不接任何动作，先积累基线数据。
2. dry-run 动作：适配层只打印将要执行的变更，用真实数据驱动状态机。
3. 受控执行：在虚拟机/备用网络执行 swap 与 rollback，验证快照恢复。
4. 逐平台固化：把每个平台的命令、权限、覆盖风险写成文档，再考虑默认开启。
