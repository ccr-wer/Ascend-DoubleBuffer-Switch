# 待验证清单（UNVERIFIED）

本仓库实际跑过的只有：`python demo.py` 与 `python -m unittest discover tests`，输入全是剧本数据，动作全是打印桩。下面每一条都没有在真实环境验证过，按"为什么未验证 / 有环境的人怎么验"列出。

## 1. A、B 劣化是否同步（共享段瓶颈）— UNVERIFIED

- **为什么未验证**：BOTH_DEGRADED 分支假设"两槽同时劣化 ≈ 上游共享段出问题，切换无意义"。剧本里 A、B 的劣化是手工对齐写出来的，不能证明真实校园里两条链路的劣化相关性，更不能证明共享段一定存在。
- **怎么验**：在真实环境同时对 A、B 做长周期探测（同一时刻成对采样），保存原始序列；计算两条序列劣化标记的相关性，并按小时段分开看。若同步劣化占比高，再逐跳 traceroute/mtr 找共同前缀，确认共享段位置；若劣化经常不同步，BOTH_DEGRADED 的权重就该下调。

## 2. 切换是否触发校园网重认证 — UNVERIFIED

- **为什么未验证**：骨架没有任何认证代码。出口 IP/MAC/会话变化是否触发 Portal 重认证、同账号能否让 A、B 并存预建，完全取决于具体学校的风控策略。
- **怎么验**：先只做被动实验——手工在两条链路间切一次默认路由，观察是否跳认证页、是否收到风控提示；再单独验证"B 预建但不走流量"是否会被判为同账号并发。任何自动化并发认证都不应在未做这两步前上线。

## 3. 各平台路由 metric / 代理分流的权限提法 — UNVERIFIED

- **为什么未验证**：动作层只有 WOULD 打印。Windows、Linux、macOS、OpenWrt 改默认路由的方式和所需权限不同，本仓库没有在任何一种系统上执行过路由变更。
- **怎么验**：按 adapter/README.md 的清单，在虚拟机或备用网络里先做 dry-run：打印将要执行的变更但不执行；确认后再在快照保护下做一次真实切换 + 回滚，记录命令、权限、耗时和回滚是否完整恢复。每个平台单独记录，不要互相推断。

## 4. 阈值标定方法 — UNVERIFIED

- **为什么未验证**：`SwitchConfig` 里的 80ms / 5% / 1Mbps 以及 window=10、ratio=0.6、cooldown=5 都是占位默认值，作用是让别人能直接跑起来，不来自任何测量分布。
- **怎么验**：先在目标环境采集足够长的健康期基线（建议覆盖不同时段），对延迟/抖动/丢包/吞吐分别取分布；阈值按 P95/P99 这类分位数取，而不是拍整数——例如延迟阈值取健康期 P99 附近，避免把正常长尾判成劣化。随后用真实故障期的数据回测：劣化检出率、误报率、从劣化到判定经过了多少个 tick，再回头调 window 与 ratio。

## 5. 预建 B 的可行性与成本 — UNVERIFIED

- **为什么未验证**：fill 在骨架里是瞬时动作，真实预建要鉴权、要建立连接、要产生流量，既可能失败也有费用/风控成本。
- **怎么验**：把 fill 拆成独立阶段单独计时与计失败率，确认它在 A 仍健康时能稳定完成；再决定它应该是常驻后台流程还是按需触发。

## 6. 切换对存量连接的影响 — UNVERIFIED

- **为什么未验证**：逻辑层没有连接概念，无法回答 TCP/QUIC 会话在出口变化后是否存活、中断多久。
- **怎么验**：在切换前后保持一条长连接（如下载、SSH），记录是否断开、重连耗时；区分"路由切换"与"出口 IP 变化"两种情形分别记录。不要用单次经验推广成普遍结论。

## 7. 窗口与冷却参数的敏感性 — UNVERIFIED

- **为什么未验证**：六场景只证明"这组参数下时序符合设计"，不证明参数在真实噪声下合理。
- **怎么验**：用真实采集的序列替换 fake_source 的剧本，对 window/ratio/cooldown 做网格回放，观察抖动导致的频繁切换（flapping）与漏判之间的取舍，再定参数。
